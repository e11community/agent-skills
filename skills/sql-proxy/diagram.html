sql-proxy · connection architecture

Laptop → Bastion → Database

sql-proxy puts a local localhost port in front of a private-IP-only Cloud SQL for PostgreSQL instance. The connection crosses two independent conduits: an IAP SSH tunnel for private-network reach, and a per-developer Cloud SQL Auth Proxy for IAM identity with an auto-refreshing token.

Laptop

your machine

  • psql / GUI / app
  • connects to localhost:5432
  • no password, no SSL to configure
IAP SSH tunnel
--tunnel-through-iap encrypted · no public IP or VPN needed

Bastion

shared VM — one lane per developer

you — cloud-sql-proxy → ~/db.sock
teammate — cloud-sql-proxy → ~/db.sock
teammate — cloud-sql-proxy → ~/db.sock

rendezvous is your own $HOME socket, namespaced by OS Login — nothing assigned

refresh token at rest: ~/.config/gcloud

Cloud SQL Auth Proxy
IAM auth · auto-refreshing token (ADC) private IP only — the only path in

Cloud SQL

PostgreSQL, private IP only

  • no public IP, ever
  • statements attributed to the individual developer
  • full per-user audit in the Postgres logs

IAP SSH tunnel — laptop ⇄ bastion. Encrypted reach into the private network; no bastion port is ever exposed publicly.

Cloud SQL Auth Proxy — bastion ⇄ database. IAM identity, auto-refreshing token, one proxy process per developer.

Credentials never reach the laptop or the database directly — they live entirely in the tunnel and proxy layer, scoped to each developer's own identity. That's what makes every statement in the Postgres logs attributable to a person, not a shared service account.
